Domain Layer
Aggregates · Value Objects · Enums · Events
Business invariants, state transitions, domain events. Pure Java — zero framework imports. Self-validating. Can be unit-tested without Spring context.
Infrastructure Layer

Persistence mapping, external messaging, technology integration. Framework-coupled (@Entity, @Repository). Changes here do not affect domain rules.
◄ ─ ─ Infrastructure mirrors Domain structure (Data Mapper pattern — separate classes) ─ ─ ►
Identity and Access Control deliberately uses a lighter structure (AuthController → FirebaseAuthService → SecurityConfig) because it represents a generic technical capability. Domain-Driven Design layering is applied selectively according to the responsibility and complexity of each area.
▲ Dependency direction: each layer depends only on the layers below it.
Domain depends on nothing. Infrastructure mirrors domain but domain does not import infrastructure.
Interface / API
Receives HTTP requests. Does not own business rules or persistence decisions. Thin layer — translates between HTTP and application concerns.
Context Façade
Single public entry point per context. Other modules and controllers interact only through this boundary. Applies @PreAuthorize for RBAC.
Domain
Pure Java. Zero framework imports. Owns all business invariants. Can be tested in milliseconds without Spring context, database, or network.
Infrastructure
Framework-coupled. @Entity, @Repository, Lombok. Mirrors domain field structure but uses separate classes (Data Mapper pattern, Lecture 4).
Arrows indicate the direction of delegation. The Domain layer has zero dependencies on any other layer. The Infrastructure layer mirrors the Domain's field structure through the Data Mapper pattern using separate JPA entity classes.
